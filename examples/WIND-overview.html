Wireless Interactive Networked Display (WIND)

A low-cost touch display controlled by a remote server. The server pushes PNG content with touch and sound maps; the device captures interaction and reports it back.

Format: stadiae-v4 Components: 3 Handlers: 5 Interfaces: 7 (+ defaults)

Components

Server Connector

4 states 1 choice point Connection lifecycle

Manages the lifecycle of the wireless connection to the server.

  • Advertises every ADVERTISEMENT ms (1000) until a server requests connection.
  • Filters incoming requests through the WhiteListed choice point against whitelist.
  • Waits at most CONNECTION_TIMEOUT ms (500) for the radio to confirm; otherwise resumes advertising.
  • On Device:ErrorInd, cancels timers, disables the radio, and falls back to Uninitialized.

Device Status Controller

3 states 1 choice point Device readiness

Determines when the device as a whole is ready, and detects peripheral failures.

  • Counts Peripherals:ReadyInd against NUM_PERIPHERALS (4) via AllReady.
  • Announces Device:ReadyInd once all peripherals are up.
  • Any Peripherals:FailureInd — before or after operational — drives a terminal Error state and emits Device:ErrorInd.

UI Controller

7 states 1 choice point Content + interaction

The most complex component: handles peripheral init, content updates, user presence, and touch interaction.

  • Tracks userPresent unconditionally via a wildcard-to-[H] transition — proximity changes never get lost regardless of current state.
  • Update transactions are gated: StartUpdateReq is accepted only when no user is interacting; otherwise rejected.
  • While Updating, touch is disabled and any number of ContentInd/SoundInd messages can be applied.
  • On UpdateDoneInd, the UserPresent choice point decides whether to re-enable touch (Interacting) or wait (ContentReady).

Interfaces

Device Connection Peripherals Content Audio Display Proximity Timer (default) Logical (default)

Connection and Content are both produced by the wireless transceiver but routed to different components: Connection goes to Server Connector, Content goes to UI Controller.

Key design points

Request-gated updates. The server cannot push content arbitrarily — every update is initiated with Content:StartUpdateReq and only proceeds after the device replies with StartUpdateAccepted. This guarantees updates cannot land mid-interaction.
Unconditional presence tracking. The userPresent flag is maintained through a wildcard transition (* → [H]) on both proximity messages, so the flag is always correct even during Updating or other transitional states.
Responsiveness rule. The touch display is only responsive when both content is loaded and a user is present. Either condition flipping makes the display unresponsive.
Terminal error condition. Once Device Status Controller enters Error, it absorbs all subsequent input (* → Error). Recovery requires reconstruction — no soft reset path.

Start-up sequence

PeripheralHandler:start() → 4× Peripherals:ReadyInd ─→ Device Status Controller emits Device:ReadyInd ├─→ Server Connector: starts advertising └─→ UI Controller: init audio → init display → sends content dimensions to server → AwaitingContent
